## Part 2 — Technical exercise

For this part, use the following contract, even if your product proposal was different.

### Rules and input

Payload: `{"available_cents":1050,"held_cents":250,"currency":"USD"}`. `available_cents` already excludes held funds. The UI must display exactly `USD 10.50 available`.

A valid transfer amount is a strict integer greater than zero, in cents. Booleans, floats, strings, zero, and negative values are invalid.

### Current code

Process the supplied input in the displayed order.

```python
def label(payload):
    return f"{payload['currency']} {payload.get('balance_cents', 0)/100:.2f} available"

def valid_amount(value):
    return isinstance(value, int) and value > 0
```

### Your tasks

Current output means what the code does as written; desired output means what the contract requires. Trace both by hand, then write your correction and extension without running them.

1. Predict label(payload) and valid_amount for [100, True, 100.0, '100', 0, -1]. Explain Python's bool/int relationship.
2. Repair the rendering contract without silently subtracting held_cents twice. Should missing required data look like a real zero?
3. Implement **preview(payload, amount)**: invalid type/value → {'ok':False,'reason':'invalid'}; valid but above available → {'ok':False,'reason':'insufficient'}; otherwise {'ok':True,'remaining_cents':...}. No mutation and no transfer is actually executed. Trace 1050 and 1051.
