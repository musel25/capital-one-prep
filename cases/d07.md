## Guía de práctica — español

Este caso tiene dos partes distintas. Primero responde la pregunta de producto con los entregables explícitos de la parte 1. Después analiza el ejemplo concreto con las reglas de la parte 2, aunque tu propuesta inicial fuera diferente. El enunciado de entrevista completo está en inglés a partir de aquí.

No ejecutes el código ni uses un agente para resolverlo. Habla en inglés y toma notas como prefieras. Guarda tu predicción antes de revelar la solución; incluye tus dudas. En los mocks cerrados, no consultes casos anteriores ni IA durante el intento.

## Part 1 — Product discussion

### What you must explain

Give a 60–90 second answer in English. You are explicitly being asked to cover all four items below; they are not hidden requirements:

1. Your proposed approach and any assumptions you would clarify.
2. The customer benefit it is intended to deliver.
3. One risk or tradeoff, including what the customer could lose.
4. Two proposed metrics: one to measure success and one to detect harm. Do not invent measured results.

Do not trace the code yet. This discussion evaluates your reasoning about a product decision; it does not determine the fixed rules in Part 2.

### Interview question

“A support assistant can answer, retrieve more context, or route to a person. How would you evaluate useful automation without rewarding unsafe answers?”

## Part 2 — Concrete technical exercise

The interviewer now supplies a specific input and a fixed contract. Follow these rules for the technical exercise even if you proposed a different product policy above. You are reviewing an existing implementation, which may violate the contract.

### A. Required behavior and supplied input

Apply these rules in order:

1. `sensitive=True` → human.
2. Language outside `{'en','es'}` → human.
3. `confidence >= 0.80` AND `approved_source=True` → answer.
4. Otherwise → search.

Scores are example data, not guarantees of correctness.

| id | sensitive | language | confidence | approved_source |
|---|---|---|---:|---|
| q1 | True | en | 0.95 | True |
| q2 | False | es | 0.80 | True |
| q3 | False | fr | 0.90 | True |
| q4 | False | en | 0.90 | False |
| q5 | False | en | 0.79 | True |
| q6 | False | es | 0.20 | False |

### B. Existing code — trace it as written

The supplied rows are passed in their displayed order. Do not assume this code implements the contract correctly.

```python
def route(q):
    if q["confidence"] >= 0.80:
        return "answer"
    if q["sensitive"]:
        return "human"
    return "search"
```

### C. Your technical tasks

First derive the **current output** by following the code exactly. Separately derive the **desired output** by applying the contract to the same input. Record intermediate state, then compare the two. Propose corrections and the requested extension on paper, without executing code.

1. Give actual and desired routes in input order and explain each mismatch.
2. Correct precedence and required evidence. What would you ask before treating a model score as calibrated confidence?
3. Implement **route_batch(rows, search_budget)**, budget is a nonnegative integer. Apply corrected routing; only search consumes one unit. When exhausted, replace further search with defer. Preserve order, return [(id,route)]. Trace budget=2 and budget=0. Do not send customer data to a real external service.

## Criterios observables

- Distingues comportamiento actual de comportamiento deseado y respetas orden, unidades y fronteras.

- Tu recomendación comercial incluye una métrica de éxito y una de riesgo, sin inventar resultados.
